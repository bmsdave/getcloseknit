# Layer load time: baseline analysis, 2026-10-23

Production (main f3933c07; the first 54 layers ran on 66f8199e, which has the same map, pack and API code), measured
through an SSH tunnel to the web container with `npm run perf:layers`. The full results are in
[2026-10-23-f3933c07.json](2026-10-23-f3933c07.json), with one row per layer × view in [history.csv](history.csv). The
metric and the method are described in [README.md](README.md).

**Read the numbers with these caveats.** The tunnel skips Caddy, so every answer arrives uncompressed and pays the
laptop ↔ OVH round trip. Main-thread time comes from the measuring laptop. Three web or API restarts by other sessions'
deploys fell inside the run (about 11:07, 12:23 and 12:52 UTC). The cold runs just after them show what the first
visitors after a deploy get, which is real, but they are noisier than a quiet server would give.

## Headline

- **The 1 s warm budget is missed by 345 of 345 layer × view pairs.** 117 catalogue layers × 3 views were tried.
  Six pairs were skipped as unpublished (`ownership-*`, not in the release).
- **Warm opens are 2–2.2 s at the median and at most 5.4 s.** Cold opens are 4.1–4.7 s at the median and at most
  18.6 s, and 3 cold pairs never settled.
- **Page boot sets a floor for an open.** A warm open of a layer whose data is already cached still takes about 2 s:
  36 JS files (2.7 MB decoded) finish at about 1.2 s even from disk cache, then MapLibre starts. The layer's own
  requests begin at about 0.2 s. The median warm open has 1.6 s of long tasks.
- **The layer's own work is small once caches are warm.** An in-app switch (a click in Layers until painted and idle,
  measured separately on production) takes 0.35–0.7 s for value-pack layers when its packs are cached. A first switch
  takes 0.5–2.6 s. Custom place layers take 2.7–2.9 s on a first switch and 1.2–1.4 s on a repeat.
- **The "tens of seconds" are cold server paths:** a price scale built per web process (10 s), the England-wide LSOA
  geometry (14 s TTFB), crime packs (6 s, fetched twice), place criteria built per request (3–5 s), and requests that
  fail and are never retried.

## Why: causes, ranked by how much they cost

1. **Cold server caches after every deploy, and some paths are never warmed.**
   - `/api/v1/price-scale` is computed in the Next.js process from every yearly price pack, the first time each
     process sees a release. It took 10.2 s and 10.6 s after the two web restarts in the run.
     `deploy/ship.sh` does not warm it.
   - It blocks every layer, not only price: `useExplorerController` puts `priceBreaks` into
     `paintedMetric(baseMetric, palette, priceBreaks)`. That returns a new object for any layer
     (`map-metric-paint.ts`, `{ ...base, legend }`), so `AreaMap` re-runs its refresh and shows "Loading map" again when
     the breaks arrive. census-birth-british-overseas painted at 11 416 ms, 10 ms after the price scale answered.
   - Value packs are built per (release, metric, period, chunk, level) in a single uvicorn process's memory
     (`EvidenceReader._packs`). `ship.sh` warms only whole, unchunked packs (`/value-packs/<id>/<period>`), but the map
     asks for chunked and rolled-up ones (`?chunk=E12000007`, `?chunk=…&level=msoa`), so those warm-ups miss.
     A crime chunk took 6.2 s cold and 0.23 s cached. The cache holds 320 000 values (`PACK_CACHE_VALUES`), about
     nine England-sized LSOA packs, so with 660 metrics it churns.
   - The ship.sh warm-up of whole packs alone took about 25 min (10:28–10:53 UTC on 2026-10-23).
2. **The first pack request asks for the wrong month (296 of 690 runs).** `AreaMap` prefetches
   `layerPackPath(props)` with `props.period`, the default month 2026-06, before the layer's own latest period is
   known. Census (2021-03) and station-access (2026-10) answer 404. Crime (2026-08) is built and sent twice: 194 runs
   fetched two periods of one layer, and for crime each copy is 1.49 MB and about 6 s of server time on the shared
   single worker.
3. **Payloads are large, and some are not cached.**
   - `/api/v1/metrics` is 1.37 MB, with no `cache-control`, on every page load, warm included. It is on the critical
     path: the layer's period and legend come from it.
   - Pack entries repeat `metricId`, `period`, `direction`, `sourceVersion` and `carrier` for each area: about 390 B
     each. A Manchester crime chunk is 116 kB raw and 2.5 kB gzipped. Census birth packs are 1.9 MB for London alone.
   - Custom place criteria (`custom:*`, the ready-made presets) POST `/api/v1/custom-criteria/evaluate`, which is
     "never cached" by design: 2.6–3.3 MB, TTFB 1–5 s, rebuilt on every open and every switch. They also cost 10
     rate-limit tokens each. The presets are not private, but they take the private path.
   - Custom layers paint with `areaGeoJsonForPack` (no pieces), so they download the **all-England LSOA polylines,
     8 MB**, even on the London view, although the criteria cover London only. That request had a 14 s TTFB when cold.
4. **Main-thread time.** A warm open has 1.6 s of long tasks at the median and 3.5–5.2 s for census layers. A CPU
   profile of a warm census open shows that the layer's own refresh is cheap (fetch 107 ms, apply 8 ms, from
   `refreshTimings`). Most of the time is boot: 2.7 MB of JS, 454 kB of CSS, MapLibre and WebGL start, and parsing the
   1.37 MB metrics catalogue. The bigger census packs add parsing and paint time on top.
5. **No retry after one failed request.** A 429 on `/api/v1/metrics`, a 503 during an API restart, or a stalled
   request leaves the map unpainted for good (3 cold timeouts and 1 warm timeout here). The visitor sees a layer that
   never loads. The harness itself can trip the shared limiter, so these four are partly self-inflicted, but the
   missing retry is real.
6. **The England view's chunk fan-out.** At z6 the map makes 14–17 requests (region packs plus shapes per region). On
   a cold server each region pack is built separately at about 1 s of TTFB.

## Proposed fixes for phase B (largest win first)

1. **Price scale off the critical path.** Keep `priceBreaks` out of `paintedMetric`'s memo for every layer except
   `price-per-square-metre`. Compute the scale in the API next to the packs, or warm it in `ship.sh`.
2. **Ask for the right month first.** Make the prefetch use the metric's default period, carried in the layer catalogue
   or a tiny per-metric index, or skip it until `metrics` resolves. This removes the 404s and the duplicate crime packs.
3. **Warm what the map actually requests.** In `ship.sh` (or a background task in the API after release activation),
   warm the coverage, the price scale, the London and region chunks at each zoom level for every metric's default
   period, the custom presets, and the geometry pieces. Make the warm-up concurrent (2–4 at a time) instead of 25 min
   sequential.
4. **A cache that outlives the process.** Persist built packs and geometry per release: a table of pre-aggregated
   packs per (metric, period, chunk, level), or files served with `immutable` and the release in the URL. A restart
   then no longer cold-starts every layer, and the 320 k-value LRU stops churning.
5. **Smaller payloads.**
   - Hoist per-pack constants out of the entries, or use `format=compact` everywhere.
   - Cache `/api/v1/metrics` for a day with the release in the URL, and split it into a light index (id, label,
     default period, carrier) plus lazily loaded details.
   - Serve the map's static JSON through Caddy compression (production already compresses; confirm Next does not
     double-handle it).
6. **Custom presets as cacheable GETs.** Serve the ready-made presets from the existing lens route
   (`/api/v1/area-values/lens/<preset>`, already warmed by ship.sh) with a release-keyed cache. Keep POST for a
   visitor's own criteria. Paint them with London's pieces, not the 8 MB all-England LSOA file.
7. **Retry with backoff** for value packs, geometry and metrics on 429, 503 or a network error, so the map does not
   stall forever.
8. **Lighter boot** (for the open metric): lazy-load what the first paint does not need, and start the MapLibre chunk
   and the style in parallel with hydration. This is the only way below about 2 s for a warm open.

**Budget proposal.** Track two numbers. The **in-app switch** (`__ckLayerTimings` with `trigger: "switch"`, budget
1 s, which is reachable: cached switches are 0.35–0.5 s today) and the **open** (budget 2.5 s warm, since boot alone
is about 2 s). The spec's strict flag currently applies the 1 s budget to the warm open.
