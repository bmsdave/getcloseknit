# Close Knit на всю Англию: что нужно и план (октябрь 2026)

Черновик на ревью владельца. Кода нет. Факты из аудита кода, данных и сервера: [audit.md](audit.md).

## Коротко

Расширение реально, и большая часть данных уже национальная: **45 из 62 источников** покрывают Англию, а Лондон из них вырезаем мы сами (фильтр E09, регион E12000007, bbox). Трудности не в данных, а в пяти местах:

1. **Ранги «против Лондона» зашиты в модель.** Это колонка `metric_value.london_percentile`, таблица `area_london_rank`, ~30 полей `londonPercentile/londonShare/londonMedian` в контракте и ~750 строк текста «London» в вебе. Нужно решить, с чем сравниваем, и ввести понятие «scope».
2. **Карта грузит все районы разом.** Геометрия и value pack сейчас 0,7 МБ и 1,4 МБ, для Англии будет ~6–10 МБ и ~10 МБ на слой. Нужны векторные тайлы с уровнями детализации.
3. **География обрывается на 33 боро.** Это enum `lsoa/msoa/borough`, триггер в миграции 001, который пускает только E09, корень `/area/london` и region IDs порталов только для 33 боро.
4. **Сервер мал.** БД вырастет с 7,3 ГБ до ~50–80 ГБ при диске 100 ГБ и 12 ГБ RAM. ETL на ноутбуке упрётся в RAM: NDVI ~15–45 ГБ, индекс EPC ~20–40 ГБ.
5. **17 источников только лондонские.** Это TfL (commute, зоны, станции), LAEI-воздух, деревья GLA, LDD, admissions 33 боро, HMO, Inside Airbnb. Часть заменяется национальными, часть остаётся «только Лондон» за флагом.

**Рекомендация.** «Англия v1» = все национальные данные (класс A) + региональные ранги + векторные тайлы + новый сервер. Лондонские фичи вне Лондона показывают «Пока только в Лондоне» (флаг, не вырезаем). Commute по всей Англии и школьные admissions идут отдельными волнами. Выкатываем сначала на пилотный регион, потом на всю Англию.

## Фазы

Зависимости: фазы 1, 2 и 4 идут параллельно. Фаза 5 ждёт 1 и 4. Фаза 7 ждёт 0 и 1. Сроки указаны в рабочих неделях при текущем темпе с агентами.

### Фаза 0. Доски (board-first), ~1 нед.
По правилу «сначала доска»: страница `england` на холсте Claude Design.
- **E1 · Англия на зуме 6–9.** Карта Англии: LAD-хлороплет → MSOA → LSOA, вход из поиска по любому английскому postcode.
- **E2 · Ранги.** Как выглядит «8/10 в South East · 6/10 в Англии». Карточка района и бейдж расширения.
- **E3 · Пробелы данных.** Чип «Пока только в Лондоне» и «грубое разрешение», на примерах воздуха, commute, admissions, деревьев.
- **E4 · Страницы регионов и LAD.** `/area/england` → регион → LAD (аналог `/area/london`), sitemap.

Готово, когда владелец согласовал E1–E4 и ответил на решения 1–7.

### Фаза 1. Модель географии и рангов, ~2 нед.
- **География.** Добавить уровни `lad` (E06/E07/E08/E09) и `region` (E12). `borough` оставить алиасом LAD для Лондона, чтобы не ломать URL. Обобщить триггер из миграции 001, enum и проверку id в `deploy/schema.sql:31-35`. Расширить `geography.py`.
- **Ранги со scope.**
  - Новая таблица `metric_rank(area_id, metric, period, scope, percentile)`, где scope = `region:E12…` или `england`.
  - `london_percentile` и `area_london_rank` заполнять из scope `region:E12000007`, так что старый код работает без изменений.
  - Обобщить `rebuild_area_london_rank()`.
- **Контракт.**
  - Новое поле `rank: {scope, percentile, share, median}` рядом со старыми.
  - `londonPercentile` и ко помечаются deprecated и остаются, пока клиенты переходят: веб, расширение, MCP.
  - `find_areas ranges scale:"percentile"` начинает означать scope района, а описание инструмента это прямо говорит.
- **Флаг покрытия** `CLOSE_KNIT_COVERAGE` со значениями `london` | `pilot` | `england` и строкой в FLAGS.md. Вне покрытия API отвечает `outside-coverage`, а не `outside-london`.
- **Одна таблица покрытия** `coverage_lad` вместо десятков хардкодов E09 и bbox в ETL. Все `etl_*` берут список LAD и bbox оттуда.

Готово, когда на текущих лондонских данных все тесты и снимки зелёные, а ранги совпадают со старыми один в один.

### Фаза 2. Доставка карты, ~2 нед.
- **Хлороплеты на векторных тайлах.**
  - MVT-функция по `area_geometry` с правильным индексом. Сейчас `ST_Transform(g.geometry,3857) && bounds` индекс не использует: нужна колонка в 3857 или трансформ bounds.
  - Уровень детализации: LAD до z8, MSOA на z9–10, LSOA с z11.
  - Тайлы геометрии статичны на релиз: PMTiles или предгенерация, cache-control immutable.
- **Значения по viewport/региону.** Value pack режется по региону или LAD, а не «весь Лондон». Нужен LRU в API по чанкам, а не 64 пакета целиком.
- **Карта:**
  - `LONDON_BOUNDS` и `MIN_MAP_ZOOM` в `web/src/lib/map-state.ts:166-192` заменить на границы покрытия.
  - Начальный вид — по гео/последнему месту.
  - `home-mini-map-canvas.tsx`, `map-street-trees.ts`.
- **Статические лондонские оверлеи** (`tfl-network.json`, `park-labels.json`) загружать только в bbox Лондона.

Готово, когда первая загрузка карты на телефоне ≤ текущей, а зум на всю Англию плавный (бюджет: замер до и после в Playwright).

### Фаза 3. Горячие пути API, ~1–2 нед.
- **`POST /api/v1/matches`** (`repository.py:244`) сейчас скорит все районы в Python без кэша. Заменить на SQL-скоринг с фильтром по scope/bbox и предрасчётом нормированных факторов на релиз.
- **`custom_criteria`.** Предрасчитать счётчики мест по LSOA на релиз; `MAX_PLACES = 60_000` для Англии не годится.
- **`personal_places`.** Ближайшее место считать через KNN-индекс PostGIS только для районов в scope.
- **Sitemap** (`web/src/app/sitemap.ts`). Шардировать по региону: будет ~70k URL при лимите Google в 50k.
- **Поиск района** (`evidence.py:157`). Индекс под нормализованное выражение. Поиск адресов на ~25M строк проверить нагрузочно.
- **`area-pages-data.ts`.** Не держать всю Англию в памяти Next: грузить по запросу и кэшировать по LAD.
- Подумать о 2+ воркерах uvicorn. Rate-limit и MCP-сессии для этого придётся вынести из памяти процесса.

### Фаза 4. Инфраструктура, ~1 нед. (параллельно)
- **Новый хост:** 32–64 ГБ RAM, 8+ dedicated, 300–500 ГБ NVMe, Лондон/UK. PG: `shared_buffers` 8–16 ГБ, `work_mem` 64–128 МБ, `maintenance_work_mem` 2 ГБ.
- **Restore без простоя.** Восстанавливать во вторую БД и переключать (сейчас `pg_restore --clean` идёт на живой базе, а для Англии это ~1–2 ч даунтайма). Бэкапы держать вне хоста.
- **ETL:**
  - NDVI/canopy обрабатывать тайлами, а не одним `np.full` на всю Англию.
  - EPC-join (`build_epc_index`) делать стримом в Postgres, а не dict в Python.
  - Либо ETL-машина 64 ГБ / 1 ТБ.
- **Долгие загрузки** перевести на bulk:
  - GBIF через download API (асинхронный экспорт вместо 10k запросов; DOI нужен и так).
  - Ofsted-отчёты подгружать фоном, после запуска.

### Фаза 5. Данные, волна A: снимаем лондонские фильтры, ~3 нед.
45 источников, у которых фильтр только наш. Порядок задан ценностью для карточки района:
1. **Основа:**
   - ONS границы и lookup, ONSPD (`civic.py:127`)
   - Census 2021, население
   - IMD 2025, доходы
2. **Цены и дома:**
   - PPD (`etl_price.py`, `bulk_price.py`; ×7 строк)
   - EPC, UK HPI, PIPR rents
   - INSPIRE: список всех советов вместо `etl_property.py:40-57`
3. **Безопасность и среда:**
   - police.uk, все силы Англии; карантин для сил с дырами уже есть
   - flood: лучше bulk NaFRA2, чем скрейп ~8k WMS-тайлов
   - noise Round 4
   - STATS19
4. **Школы и дети:** GIAS/KS2/KS4/KS5 (`LONDON_LAS`), Ofsted MI, applications/offers, Ofsted childcare.
5. **Места:** OSM `england-latest.pbf`, Overture, FSQ (снять guard 4 ГБ или читать чанками), FHRS (~300 XML).
6. **Дом и сервис:**
   - Ofcom broadband/mobile
   - VOA CTSOP
   - council tax: в двухуровневых районах округ + district + police + fire, это новая логика
   - GP, CCOD/OCOD
7. **Гражданское:** councillors (выборы по третям и половинам, нужен календарь по каждому совету), MPs, planning.data.gov.uk (частичное покрытие, видно в UI).
8. **Природа:** Natural England (уже национальное), OS Open Roads, Sentinel-2 (~80–150 ГБ сырья) последним.

Для каждого источника: прогон на пилотном регионе → проверка (data-validation) → вся Англия → строка в DATA-LICENCES.md.

## Оценка

- **Календарь:** ~8–12 недель до «Англия v1» на пилоте, ещё ~2 недели до всей Англии.
- **Деньги:** сервер ~£20 → ~£80–100/мес. Google Places растёт пропорционально числу агентств.
- **Главные риски:**
  1. Ранги: решение 1 меняет смысл многих экранов.
  2. Производительность первой загрузки карты.
  3. ETL-время (GBIF, Ofsted, Sentinel) и RAM.
  4. Пользователи вне Лондона увидят меньше фич: важно честное «пока только в Лондоне».

## Что можно начать сразу, не дожидаясь досок
Это чисто техническая работа, она ничего не меняет для пользователя:
- Фаза 4 (сервер, restore без простоя, ETL чанками).
- Таблица `coverage_lad` и вынос хардкодов E09/bbox из ETL (фаза 1, без UI).
- Индекс в MVT `area_geometry` и прототип тайлов хлороплета (фаза 2).
